# Chapter 11 — Context Compiler Deep Dive

## 11.1 The Philosophy

The Andalus context compiler solves one specific problem: **given a Java file being edited, and a token budget, assemble the most useful verbatim context — never a summary.**

The design is grounded in a hard constraint: **every character the compiler emits is a substring of the original source.** Scope narrows (which members are shown); fidelity never drops (how they're shown). There is no "here's a summary of what this file does" tier. Ever.

```mermaid
flowchart TB
    TARGET[Target File] --> TIER1[Tier 1: Full Source]
    TIER1 --> DIFF{Hop Distance}

    DIFF -->|1 hop| TIER2[Tier 2: Full Skeleton]
    DIFF -->|1 hop, tight budget| TIER2P[Tier 2b: Pruned Skeleton]
    DIFF -->|1 hop, very tight| TIER3[Tier 3: Signature Digest]
    DIFF -->|> maxHops| TIER4[Tier 4: Excluded]

    TIER1 --> ASM[Prompt Assembly]
    TIER2 --> ASM
    TIER2P --> ASM
    TIER3 --> ASM
    ASM --> PROMPT[Compiled Prompt]

    style TIER1 fill:#27AE60,color:#fff
    style TIER2 fill:#4A90D9,color:#fff
    style TIER2P fill:#F39C12,color:#fff
    style TIER3 fill:#E67E22,color:#fff
```

## 11.2 The Six Tiers

| Tier | Name | What's shown | Fidelity |
|------|------|--------------|----------|
| **1** | `FULL_SOURCE` | The file being edited | 100% verbatim |
| **1b** | `SOURCE_CHUNK` | Line window of a large file | 100% verbatim |
| **2** | `SKELETON` | Reachable file: every member's signature + Javadoc, bodies stripped | 100% verbatim (bodies replaced with stubs) |
| **2b** | `SKELETON_PRUNED` | Only members confidently attributed as *used* | 100% verbatim |
| **3** | `SIGNATURE_DIGEST` | Bare signatures, one line per member | 100% verbatim |
| **4** | `EXCLUDED` | Nothing | N/A |

## 11.3 The Compilation Pipeline

```mermaid

    C->>MB: build(repoRoot)
    MB->>MB: walk(*.java)
    MB->>MB: parse package + types
    MB-->>C: ModuleIndex

    C->>SR: resolve(index, targetFile, maxHops)
    SR->>SR: BFS outward from target
    SR->>SR: resolve imports + same-package
    SR->>SR: bare method-name fallback
    SR->>SR: flag reflection / event annotations / collisions
    SR-->>C: ReachabilityResult

    C->>RS: score(each reachable file)
    RS-->>C: ranked file list

                    TE-->>C: tokens
```

## 11.4 Symbol Resolution — The Three Blind Spots

The `HeuristicSymbolResolver` trades soundness for speed. Three blind spots follow from that trade-off, and each is **disclosed** rather than hidden.

### Blind Spot 1: Reflection-Based Dispatch

```java
Class<?> clazz = Class.forName(className);
clazz.getDeclaredMethod("run").invoke(clazz.getDeclaredConstructor().newInstance());
```

The resolver detects `forName`, `getMethod`, `getDeclaredMethod`, `invoke`, `newInstance` and adds the file to `dynamicDispatchFiles`.

**Reported as:**
```
Warning: 1 file(s) use reflection-based dynamic dispatch — targets may be missing from tier 2.
```

### Blind Spot 2: Event-Style Annotations

```java
@ConsumeEvent
public void onOrderPlaced(String orderId) {
    // ...
}
```

The resolver detects `@Observes`, `@ObservesAsync`, `@ConsumeEvent`, `@Incoming`, `@Outgoing`, `@Scheduled` and records them as `eventAnnotationHints`.

**Reported as:**
```
Warning: 1 file(s) use event-style annotations (e.g. @Observes, @ConsumeEvent) — handlers may be missing from tier 2.
```

### Blind Spot 3: Name Collisions

```java
// UserRepository.java
public void save() { ... }

// OrderRepository.java
public void save() { ... }
```

A bare `save()` call matches both. The resolver adds both files to Tier 2 and records the collision.

**Reported as:**
```
Note: 1 call name(s) resolved to more than one file (name-only resolution) — tier 2 may include false positives.
```

## 11.5 The Type-Aware Resolver (Optional Upgrade)

`TypeAwareSymbolResolver` wraps `HeuristicSymbolResolver` and uses JavaParser's symbol solver to narrow name-collision candidates when a project-wide type solver is available.

```java
Path sourceRoot = Path.of("src/main/java");
SymbolResolver resolver = new TypeAwareSymbolResolver(sourceRoot);
```

When the symbol solver resolves a call, it narrows to the declaring type's file. When it can't (unresolved imports, external jars), it falls back to the heuristic result — never silently guesses.

## 11.6 Skeletonization Levels

### Tier 2 — Full Skeleton

Every member's signature + Javadoc preserved. Bodies replaced with stubs:

```java
public class UserService {
    /**
     * Persists the current user.
     */
    public void save() {
        // body stripped
    }

    public User findById(String id) {
        return null; // body stripped, default value inserted
    }
}
```

### Tier 2b — Pruned Skeleton

Only members in the `keepMemberNames` set are shown. Constructors and fields are always kept.

```java
public class UserService {
    // pruned: 8 member(s) not reachable from target, omitted

    private final UserRepository userRepository;

    /**
     * Persists the current user.
     */
    public void save() {
        // body stripped
    }
}
```

### Tier 3 — Signature Digest

One line per member, no Javadoc, no annotations:

```java
public class UserService {
    private UserRepository userRepository;
    public void save();
    public User findById(String id);
    public List<User> findAll();
}
```

## 11.7 Budget-Aware Greedy Knapsack

The `DefaultBudgetedContextCompiler` uses a greedy knapsack algorithm:

1. **Rank** reachable files by `RelevanceScorer.score()`
2. **For each file** (in rank order), try the richest representation that fits remaining budget
3. **Spill** to the next leaner tier if the richer one doesn't fit
4. **Exclude** if even the digest doesn't fit

The scorer is deliberately explainable — every score is derivable from `ReachabilityResult` alone:

```
score = 1/hop + 0.1 × callSiteCount + 0.05 × usedMemberCount
```

No embeddings, no LLM calls. Just hop distance, call-site count, and member attribution confidence.

## 11.8 The Context Planner

`DefaultContextPlanner` maps task intent to `ContextPlan`:

| Intent | maxHops | Budget | Rationale |
|--------|---------|--------|-----------|
| `BUG_FIX` | 2 | 65% of window | Shallow and precise — defect is near the symptom |
| `REFACTOR` | 3 | 65% of window | Wider blast radius — callers 2-3 hops out need visibility |
| `NEW_FEATURE` | 2 | 52% of window | Moderate depth, budget held for new code generation |
| `EXPLORATION` | 4 | 65% of window | Cast wide, coverage > precision |

`GENERATION_RESERVE = 0.35` — 35% of the window is always reserved for the model's own reasoning and output tokens.

## 11.9 Source Chunking

For large files, `SourceCodeChunker` splits into overlapping line windows:

- **Default:** 200 lines per chunk, 20 lines overlap
- **Overlap** ensures context isn't lost at chunk boundaries
- **Chunks** are the unit for `SOURCE_CHUNK` (Tier 1b)

```java
SourceCodeChunker chunker = new SourceCodeChunker();
List<SourceChunk> chunks = chunker.chunk(path);
// Each chunk has: path, range (start/end/index), content, metadata (language, checksum, tokens)
```

# Chapter 12 — Workflow & Graph Engine

## 12.1 Two Workflow Engines

Andalus ships two distinct workflow engines, serving different needs:

| Engine | Module | Model | Best for |
|--------|--------|-------|----------|
| **State-Machine Graph** | `andalus-orchestration` | Nodes + edges + reducers | Agent coordination, LLM-driven flows |
| **Workflow Definition** | `andalus-workflow` | Steps + transitions | Business process, deterministic flows |

Both can delegate to a `WorkflowBackend` (e.g., Gamelan) for durable execution.

## 12.2 The State-Machine Graph

### 12.2.1 Core Concepts

```mermaid
classDiagram
    class WorkflowGraph {
        +addNode(name, node) WorkflowGraph
        +addEdge(from, to) WorkflowGraph
        +addConditionalEdge(from, edge) WorkflowGraph
        +setEntryPoint(name) WorkflowGraph
        +withCheckpointStrategy(strategy) WorkflowGraph
        +compile() CompiledWorkflow
    }

    class CompiledWorkflow {
        +invoke(initialState, threadId) GraphState
    }

    class GraphNode {
        <<interface>>
        +execute(state) StateUpdate
    }

    class GraphState {
        +apply(update) void
        +get(key) T
        +withReducer(key, reducer) GraphState
    }

    class StateUpdate {
        +put(key, value) StateUpdate
    }

    class StateReducer~T~ {
        <<interface>>
        +reduce(current, update) T
    }

    class ConditionalEdge {
        <<interface>>
        +next(state) String
    }

    class CheckpointStrategy {
        <<interface>>
        +save(threadId, state) void
        +load(threadId) GraphState
    }

    WorkflowGraph --> CompiledWorkflow
    CompiledWorkflow --> GraphNode
    CompiledWorkflow --> GraphState
    CompiledWorkflow --> CheckpointStrategy
    GraphState --> StateReducer
    GraphState --> StateUpdate
    WorkflowGraph --> ConditionalEdge
```

### 12.2.2 Reducers

Reducers define how state updates merge into existing state. The default is `OverwriteReducer` (last write wins).

```java
// Append reducer — accumulate messages
GraphState state = new GraphState()
    .withReducer("messages", new AppendReducer<ChatMessage>());
```

Custom reducer:

```java
public class SumReducer implements StateReducer<Integer> {
    @Override
    public Integer reduce(Integer current, Integer update) {
        return (current == null ? 0 : current) + (update == null ? 0 : update);
    }
}
```

### 12.2.3 The Execution Loop

```mermaid
sequenceDiagram
    participant C as Caller
    participant W as CompiledWorkflow
    participant CS as CheckpointStrategy
    participant N as GraphNode
    participant S as GraphState

    C->>W: invoke(initialState, threadId)
    W->>CS: load(threadId)

    alt checkpoint exists
        CS-->>W: savedState
        W->>S: use savedState
    else no checkpoint
        CS-->>W: null
        W->>S: use initialState
    end

    W->>S: get("__next_node__")
    alt no next node
        W->>W: currentNode = entryPoint
    end

    loop Until currentNode == "__END__"
        W->>N: node.execute(state)
        N-->>W: StateUpdate
        W->>S: state.apply(update)

        alt conditional edge
            W->>W: next = conditionalEdge.next(state)
        else regular edge
            W->>W: next = edges.get(currentNode)
        end

        W->>S: apply(StateUpdate.put("__next_node__", next))
        W->>CS: save(threadId, state)
        W->>W: currentNode = next
    end

    W-->>C: finalState
```

# Chapter 13 — Advanced Security

## 13.1 The Threat Model

Andalus assumes the following threats:

| Threat | Mitigation |
|--------|------------|
| **Prompt injection via tool args** | Guardrails pre-check + schema validation |
| **Privilege escalation via delegation** | Strict attenuation (child ⊆ parent) |
| **Cross-tenant data leakage** | Tenant isolation policies on every protocol |
| **Audit evasion** | Append-only event ledger + audit sink |
| **Sensitive data exfiltration** | PII detection + redaction obligations |
| **Untrusted downstream agents** | Trust service + propagation modes |
| **Replay attacks** | Nonces + request binding fingerprints |
| **Supply chain (tools)** | Capability declarations + approval gates |

## 13.4 Delegation Attenuation

### 13.4.1 The Invariant

**Child authority ⊆ parent authority** across every dimension:

- Capabilities: `child.caps ⊆ parent.caps`
- Actions: `child.actions ⊆ parent.actions`
- Hops: `child.maxHops ≤ parent.maxHops - 1`

### 13.4.2 The Attenuator

```java
public final class DefaultDelegationAttenuator implements DelegationAttenuator {
    @Override
    public DelegationConstraints attenuate(
            DelegationConstraints parent,
            DelegationConstraints requested) {

        List<String> capabilities = intersect(parent.allowedCapabilities(), requested.allowedCapabilities());
        List<String> actions = intersect(parent.allowedActions(), requested.allowedActions());
        int maxHops = Math.min(Math.max(0, parent.maxHops() - 1), requested.maxHops());

        return new DelegationConstraints(capabilities, actions, maxHops);
    }

    private List<String> intersect(List<String> parent, List<String> requested) {
        if (parent.contains("*")) return requested;
        if (requested.contains("*")) return parent;
        List<String> result = new ArrayList<>(parent);
        result.retainAll(requested);
        return List.copyOf(result);
    }
}
```

```java
public final class KnowledgeEvidenceExchangeFlowControlWindow {

    public boolean tryConsume(long bytes) {
        while (true) {
            long current = availableBytes.get();
            if (current < bytes) return false;
            if (availableBytes.compareAndSet(current, current - bytes)) return true;
        }
    }

    public void update(long bytes) { availableBytes.addAndGet(bytes); }
```

### 15.4.2 Conflict Resolution Policy

The default resolver is deliberately conservative:

```java
public final class DefaultKnowledgeAnswerResolutionReplicationConflictResolver
        implements KnowledgeAnswerResolutionReplicationConflictResolver {

    @Override
    public KnowledgeAnswerResolutionMemoryEntry resolve(
            List<KnowledgeAnswerResolutionMemoryEntry> candidates) {

        if (candidates == null || candidates.isEmpty()) return null;
        if (candidates.size() == 1) return candidates.get(0);

        /*
         * Do not silently choose between concurrent
         * authoritative resolutions.
         *
         * A higher-level resolution process should
         * compare their underlying answer artifacts.
         */
        return null;
    }
}
```

This forces the caller to escalate to a higher-level resolution process rather than silently picking one.

### 16.2.2 Cache Key Design

The `ExecutionCache.hashInputs` method produces a deterministic SHA-256 from a sorted map:

```java
static String hashInputs(Map<String, Object> arguments) {
    var sorted = new TreeMap<>(arguments);
    String canonical = sorted.toString();
    var digest = MessageDigest.getInstance("SHA-256");
    return hex(digest.digest(canonical.getBytes(UTF_8)));
}
```

Sorting keys means argument order doesn't affect the hash.

### 16.2.3 Cache Invalidation

1. **TTL-based** — entries expire after `ttl`

### 16.5.2 Batch Deduplication

Before dispatching, the pipeline deduplicates inputs by cache key:

```java
Map<String, List<Integer>> missingByKey = new LinkedHashMap<>();
for (int i = 0; i < inputs.size(); i++) {
    String key = buildCacheKey(...);
    if (cacheEnabled) {
        float[] cached = vectorCache.get(key);
        if (cached != null) {
            resolved.put(i, cached);
            continue;
        }
    }
    missingByKey.computeIfAbsent(key, k -> new ArrayList<>()).add(i);
}
```

This means duplicate inputs only hit the provider once, and cache hits short-circuit entirely.

```java
public final class KnowledgeEvidenceExchangeFlowControlWindow {
    private final AtomicLong availableBytes;

    public boolean tryConsume(long bytes) {
        while (true) {
            long current = availableBytes.get();
            if (current < bytes) return false;
            if (availableBytes.compareAndSet(current, current - bytes)) return true;
        }
    }

}
```

## 16.11 Memory Optimization

### 16.11.1 Memory Hierarchy

The four-tier memory model naturally optimizes memory:

- **Working** — small, token-budgeted, cleared per task
- **Episodic** — conversation history, bounded by maxMessages
- **Semantic** — extracted concepts/facts, deduplicated
- **Procedural** — task patterns, proficiency-scored

### 16.11.2 Conversation Windowing

`ConversationMemory` trims history to fit both message count and token budget:

```java
ConversationMemory memory = new ConversationMemory(
    50,    // maxMessages
    8000   // maxTokenBudget
);
```

When either limit is exceeded, oldest messages are dropped first.

### 16.11.3 Tool Result Compression

Large tool results are compressed before being added to memory:

```java
if (result.length() > 6000) {
    stored = result.substring(0, 3000)
        + "\n\n...[result compressed]...\n\n"
        + result.substring(result.length() - 1500);
}
```

This keeps the first and last portions (typically most informative) while dropping the middle.

# Chapter 18 — Migration & Upgrade Guide

## 18.1 Version Compatibility

Andalus follows semantic versioning with a strict compatibility policy:

| Version | Compatibility |
|---------|---------------|
| **Patch** (1.0.x) | Bug fixes only, no API changes |
| **Minor** (1.x.0) | Backward-compatible additions |
| **Major** (x.0.0) | Breaking changes, migration required |

### 18.1.1 Compatibility Matrix

| From \ To | 1.0.x | 1.1.x | 2.0.x |
|-----------|-------|-------|-------|
| **1.0.x** | ✅ | ✅ | ⚠️ Migration |
| **1.1.x** | ❌ | ✅ | ⚠️ Migration |
| **2.0.x** | ❌ | ❌ | ✅ |

## 18.2 Migrating from 1.0 to 1.1

### 18.2.1 Agent API Changes

**Before (1.0):**
```java
AndalusAgent agent = new AndalusAgent(provider, memory);
agent.send("Hello", listener);
```

**After (1.1):**
```java
ReActAgent agent = new ReActAgent();
agent.setProvider(provider);
agent.setMemory(memory);
agent.send("Hello", listener);
```

The `AndalusAgent` class was renamed to `ReActAgent` and moved from `tech.kayys.andalus.agent` to `tech.kayys.andalus.agent.react`.

### 18.2.2 Tool API Changes

**Before (1.0):**
```java
public interface Tool {
    String name();
    String description();
    Object execute(Map<String, Object> args);
}
```

**After (1.1):**
```java
public interface Tool extends Extension {
    ToolDescriptor descriptor();
    CompletableFuture<ToolResult> execute(ToolInvocation invocation, ToolContext context);
}
```

Migration steps:

1. Replace `name()` and `description()` with a `descriptor()` method
2. Change `execute` return type from `Object` to `CompletableFuture<ToolResult>`
3. Wrap results in `SimpleToolResult.success(...)` or `.failure(...)`
4. Add `id()`, `type()`, `metadata()` methods (or extend `AbstractEipTool`)

### 18.2.3 Communication API Changes

**Before (1.0):**
```java
AgentRequest request = new AgentRequest(target, payload);
communicator.send(request);
```

**After (1.1):**
```java
AgentRequest request = new AgentRequest(
    target,
    CapabilityId.of("default"),
    payload,
    RequestMode.AUTO,
    Duration.ofSeconds(60),
    CommunicationOptions.automatic(),
    Map.of()
);
communicator.send(request, ProtocolContext.empty());
```

## 18.3 Migrating from 1.1 to 2.0

### 18.3.1 Execution Kernel API

The biggest change in 2.0 is the introduction of the `ExecutionPipeline` interceptor model. Direct calls to `ExecutionEngine.executeAgent` are deprecated.

**Before (1.1):**
```java
ExecutionEngine engine = ...;
ExecutionResult result = engine.executeAgent(definition, context);
```

**After (2.0):**
```java
ExecutionPipeline pipeline = ...;
AgentInvocation invocation = invocationFactory.root(request, security);
AgentResult result = pipeline.execute(invocation).toCompletableFuture().join();
```

### 18.3.2 Security Model

**Before (1.1):**
```java
// Security was per-communicator
AgentCommunicator communicator = new SecuredAgentCommunicator(delegate, authz);
```

**After (2.0):**
```java
// Security is on the invocation path
ExecutionPipeline pipeline = new DefaultExecutionPipeline(
    interceptorPipeline,
    terminalHandler
);
// Interceptors include AuthorizationInterceptor
```

### 18.3.3 Migration Checklist

- [ ] Replace `ExecutionEngine.executeAgent` with `ExecutionPipeline.execute`
- [ ] Replace `SecuredAgentCommunicator` with `AuthorizationInterceptor`
- [ ] Update `AgentRequest` construction to include `CapabilityId` and `CommunicationOptions`
- [ ] Migrate `Tool.execute` to `CompletableFuture<ToolResult>`
- [ ] Update `Agent` implementations to extend `BaseReActAgent`
- [ ] Replace `AgentListener` with `AndalusAgentListener`
- [ ] Update A2A models to 1.0 spec (`AgentCard` → `A2AAgentCard`)
- [ ] Update ANP models to 1.1 spec (`DID:WBA` prefix required)
- [ ] Migrate memory from `Memory<ChatMessage>` to the four-tier model
- [ ] Update knowledge models to include `KnowledgeItem` with provenance
- [ ] Replace `GuardrailsService.preCheck(String, Map)` with the plugin API

## 18.4 Deprecation Policy

Deprecated APIs are marked with `@Deprecated` and remain functional for **one major version**. The `@Deprecated` annotation includes:

- `since` — version when deprecated
- `forRemoval` — whether it will be removed
- `description` — replacement API

Example:

```java
@Deprecated(since = "1.1.0", forRemoval = true)
public void oldMethod() {
    // Replacement: newMethod()
}
```

## 18.5 Upgrade Procedure

### 18.5.1 Pre-Upgrade Checklist

1. **Backup** all data stores (PostgreSQL, Redis, Neo4j)
2. **Snapshot** all durable A2A tasks
3. **Export** all knowledge snapshots
4. **Record** current versions of all dependencies
5. **Review** release notes for breaking changes
6. **Test** upgrade in staging environment

### 18.5.2 Upgrade Steps

```mermaid
flowchart TD
    START[Start] --> STOP[Stop all Andalus instances]
    STOP --> BACKUP[Backup data stores]
    BACKUP --> UPDATE[Update dependencies in pom.xml]
    UPDATE --> BUILD[Build new version]
    BUILD --> MIGRATE[Run DB migrations]
    MIGRATE --> START1[Start one instance]
    START1 --> HEALTH{Health check?}
    HEALTH -->|fail| ROLLBACK[Rollback]
    HEALTH -->|ok| START_ALL[Start all instances]
    START_ALL --> VERIFY[Verify functionality]
    VERIFY --> DONE[Done]
    ROLLBACK --> DONE

    style HEALTH fill:#F39C12,color:#fff
    style ROLLBACK fill:#E74C3C,color:#fff
    style DONE fill:#27AE60,color:#fff
```

### 18.5.3 Rollback Procedure

If upgrade fails:

1. **Stop** new instances
2. **Restore** data stores from backup
3. **Revert** dependency versions
4. **Rebuild** old version
5. **Restart** old instances
6. **Verify** functionality

## 18.6 Data Migration

### 18.6.1 Knowledge Store Migration

```java
public class KnowledgeStoreMigration {

    public void migrateV1ToV2(DataSource dataSource) {
        // 1. Add new columns
        execute(dataSource, """
            ALTER TABLE knowledge_items
            ADD COLUMN provenance_uri TEXT,
            ADD COLUMN authority_kind VARCHAR(50),
            ADD COLUMN trust_level VARCHAR(20) DEFAULT 'REVIEWED',
            ADD COLUMN revision BIGINT DEFAULT 1
            """);

        // 2. Backfill provenance
        execute(dataSource, """
            UPDATE knowledge_items
            SET provenance_uri = source_url
            WHERE provenance_uri IS NULL AND source_url IS NOT NULL
            """);

        // 3. Backfill authority
        execute(dataSource, """
            UPDATE knowledge_items
            SET authority_kind = 'informational'
            WHERE authority_kind IS NULL
            """);

        // 4. Add indexes
        execute(dataSource, """
            CREATE INDEX idx_knowledge_validity
            ON knowledge_items(effective_from, effective_until)
            """);
    }

    private void execute(DataSource ds, String sql) {
        try (var conn = ds.getConnection();
             var stmt = conn.createStatement()) {
            stmt.execute(sql);
        } catch (SQLException e) {
            throw new RuntimeException("Migration failed: " + sql, e);
        }
    }
}
```

## 18.8 Configuration Migration

Configuration keys are versioned. The `ConfigurationMigration` service auto-migrates old keys:

```java
public class ConfigurationMigration {

    private static final Map<String, String> KEY_MAPPINGS = Map.of(
        "andalus.agent.model", "andalus.provider.model",
        "andalus.agent.provider", "andalus.provider.name",
        "andalus.tools.directory", "andalus.tool.directory",
        "andalus.memory.type", "andalus.memory.default-tier"
    );

    public Configuration migrate(Configuration old) {
        Map<String, Object> migrated = new LinkedHashMap<>();
        old.asMap().forEach((key, value) -> {
            String newKey = KEY_MAPPINGS.getOrDefault(key, key);
            migrated.put(newKey, value);
        });
        return new DefaultConfiguration(migrated);
    }
}
```

# Chapter 20 — Roadmap & Future

## 20.1 Near-Term (Next 6 Months)

### 20.1.1 Native Image Support

GraalVM native image compilation for Andalus runtime, targeting:

- **Startup time:** < 100 ms (vs ~2s JVM)
- **Memory footprint:** < 100 MB (vs ~500 MB JVM)
- **Distribution:** single binary, no JVM required

**Challenges:**

- Reflection (JavaParser, Jackson) requires `reflect-config.json`
- Virtual threads are not yet supported in native image (as of GraalVM 24)
- CDI proxy generation needs build-time hints

**Approach:** Provide `@RegisterForReflection` annotations and a native-image configuration module.

### 20.1.2 gRPC Transport

Add gRPC as a first-class transport for A2A and knowledge exchange:


**Benefits:**

- **Bidirectional streaming** — native support
- **Multiplexing** — multiple streams per connection
- **Schema-first** — protobuf IDL
- **Performance** — lower overhead than JSON-RPC

## 20.4 Research Directions

### 20.4.1 Context Compilation with Neural Ranking

The current relevance scorer is purely mechanical (hop distance, call-site count, member attribution). A neural ranker could improve context selection:

- **Training data:** Edit → accepted changes
- **Model:** Small transformer (e.g., CodeBERT)
- **Input:** Target file + candidate files
- **Output:** Relevance score

**Challenge:** Must remain explainable. A neural ranker that can't explain its choices violates Andalus's transparency principle.

### 20.4.2 Continuous Learning from Tool Failures

When a tool fails, learn from it:

- **Failure pattern** — what arguments cause failures?
- **Recovery strategy** — what alternative tools work?
- **Prevention** — how to avoid the failure next time?

Store in procedural memory:

```java
ProceduralMemory.record(
    taskPattern: "search-github-repos",
    tool: "github-search",
    failure: "rate-limited",
    recovery: "wait 60s then retry",
    proficiency: 0.8
);
```

### 20.4.3 Multi-Agent Negotiation

Move from orchestration to negotiation:

- **Bidding** — agents bid on tasks based on capability and load
- **Contract net** — task announcement + bid + award
- **Auction** — English, Dutch, Vickrey

```mermaid
sequenceDiagram
    participant C as Coordinator
    participant A1 as Agent 1
    participant A2 as Agent 2
    participant A3 as Agent 3

    C->>A1: announce(task)
    C->>A2: announce(task)
    C->>A3: announce(task)

    A1-->>C: bid(cost=10, time=5s)
    A2-->>C: bid(cost=8, time=10s)
    A3-->>C: bid(cost=15, time=2s)

    C->>C: select winner
    C->>A2: award(task)
    A2-->>C: accept
```

### 20.4.4 Adversarial Robustness

Test agents against adversarial inputs:

- **Prompt injection** — malicious instructions in tool results
- **Jailbreak** — attempts to bypass guardrails
- **Data poisoning** — corrupted knowledge sources
- **Model extraction** — attempts to steal the model

Build an adversarial test suite that runs on every release.

### 20.4.5 Causal Reasoning

Move from correlation to causation:

- **Causal graphs** — explicit cause-effect relationships
- **Counterfactuals** — "what if we had done X?"
- **Interventions** — actively test hypotheses

**Use case:** Root cause analysis in debugging agents.

## 20.7 Conclusion

Andalus's architecture is designed for **longevity**. The core principles — protocol-agnostic communication, verbatim context compilation, explicit blind-spot disclosure, and durable execution — are not tied to any specific LLM or vendor. As the AI landscape evolves, Andalus can adopt new models, new protocols, and new techniques without rearchitecting.

The roadmap above is ambitious but grounded. Every feature listed is a natural extension of an existing principle, not a departure from it. That's the mark of a system built to last.

### H.4 Key Differences

Andalus differs from these frameworks in three important ways:

1. **Execution Kernel is first-class.** Frameworks like LangChain4j and Spring AI treat execution as a series of function calls. Andalus has a dedicated Execution Kernel that owns checkpoints, journals, ledgers, budgets, and lifecycle. This enables durable executions, time-travel debugging, and uniform observability.

2. **Protocol-agnostic.** Andalus's communication layer is protocol-agnostic from the start. A2A, ANP, and local protocols are projections of canonical models. This makes federation and interop trivial — you don't need to rewrite agent logic to expose it via a different protocol.

3. **Context compilation is verbatim.** Andalus never summarizes context. It reduces *scope* (which members are shown), never *fidelity* (how they're shown). This is a deliberate philosophical choice that trades context compression for trust.
